# Chapter 23 — Simulation, Validation, and Debug

## 23.1 Overview

**Simulation, validation, and debug** are the final technical activities used to confirm that the FPGA Video Color Processing System behaves correctly before and after deployment to hardware. Simulation verifies RTL behavior in tools such as ModelSim or Questa. Validation confirms that the implemented design produces correct image results. Debug identifies and isolates failures in the video stream, register interface, image-processing logic, timing, or software control path.

The source design states that the K-means module was synthesized and implemented using **Vivado 2022.1** for the Kria KV260 board and verified using **ModelSim 2020 Edition**. It also describes a filter verification approach where a VHDL testbench reads an image file, applies RGB stimulus, waits until the end of frame, and generates a valid output BMP image.

A complete validation flow is:

RTL Simulation

↓

Image-Based Output Checking

↓

UVM Register and Protocol Testing

↓

Synthesis and Implementation

↓

Hardware Bring-Up

↓

Live Camera Validation

↓

Display / Ethernet Output Debug

The purpose of this chapter is to define a repeatable engineering method for proving that the system works and for diagnosing failures when it does not.

## 23.2 Simulation Objectives

Simulation verifies the design before FPGA programming. It should confirm both functional correctness and protocol correctness.

Primary simulation objectives include:

| **Objective**     | **Description**                                                                 |
|-------------------|---------------------------------------------------------------------------------|
| RTL correctness   | Verify that each module produces the expected output.                           |
| Register behavior | Confirm AXI4-Lite read/write transactions and register side effects.            |
| Pixel processing  | Validate filters, color conversions, CCM, K-means, histogram, and segmentation. |
| Frame timing      | Verify start-of-frame, end-of-line, valid, and frame counters.                  |
| Reset behavior    | Confirm all state machines and registers recover cleanly.                       |
| Pipeline latency  | Measure and align expected versus actual output timing.                         |
| Error handling    | Confirm timeout, overflow, invalid mode, and protocol error reporting.          |
| Output generation | Confirm output image files or streams are generated correctly.                  |

Simulation should be performed at multiple levels: block level, subsystem level, and system level.

## 23.3 Simulation Levels

### 23.3.1 Block-Level Simulation

Block-level simulation targets one module at a time.

Examples:

- RGB to HSL.

- HSL to RGB.

- Color correction matrix.

- Sharp filter.

- Blur filter.

- Emboss filter.

- Sobel filter.

- K-means clustering.

- Histogram counter.

- Local threshold segmentation.

Block-level simulation is useful because failures are easier to isolate.

### 23.3.2 Subsystem-Level Simulation

Subsystem simulation includes the VCP control path and selected processing modules.

AXI4-Lite Register Driver

↓

VCP Register Bank

↓

Selected Processing Module

↓

Output Monitor

This verifies that software-visible register writes correctly activate the intended video-processing behavior.

### 23.3.3 System-Level Simulation

System-level simulation includes camera-like stimulus, register configuration, video pipeline, and output checking.

Camera Stimulus

↓

VCP DUT

↓

Output Frame Monitor

↓

Scoreboard / BMP Output

System-level simulation confirms that the full design works as an integrated video pipeline.

## 23.5 Waveform-Based Debug

Waveform inspection is essential when a simulation mismatch occurs. The source document includes RGB-to-HSL simulation wave diagrams and notes that the simulation results of RGB channel conversion to HSL are presented in a wave diagram.

Waveforms should include:

| **Signal Group** | **Signals**                                     |
|------------------|-------------------------------------------------|
| Clock/reset      | clk, reset, aresetn                             |
| Video input      | iRgb.red, iRgb.green, iRgb.blue, iRgb.valid     |
| Video control    | sof, eol, eof, tuser, tlast                     |
| Register bus     | AWADDR, WDATA, WSTRB, ARADDR, RDATA, responses  |
| Internal state   | FSM states, mode selection, active filter ID    |
| Pipeline valid   | Valid delay chain, output valid                 |
| Output pixel     | oRgb.red, oRgb.green, oRgb.blue, oRgb.valid     |
| Error flags      | Timeout, overflow, protocol error, invalid mode |

The first debug objective is to determine whether the failure is caused by input stimulus, register configuration, internal computation, or output alignment.

## 23.6 Register and AXI4-Lite Simulation

Register simulation confirms that the control interface operates correctly. The source driver describes AXI4-Lite read/write behavior using handshaking and includes timeout checks when responses do not arrive within the expected clock window.

AXI4-Lite simulation should verify:

- Write address handshake.

- Write data handshake.

- Write response.

- Read address handshake.

- Read data response.

- Byte strobes.

- Reserved-bit behavior.

- Invalid address behavior.

- Back-to-back transactions.

- Reset during transaction.

The source verification code includes timeout checks for AWVALID, BVALID, ARVALID, and RVALID, plus response-error checks for write and read transactions.

## 23.7 Simulation Pass/Fail Criteria

A simulation should not be considered passing only because it finishes. It must satisfy measurable criteria.

| **Criterion**          | **Required Result**                                           |
|------------------------|---------------------------------------------------------------|
| No fatal errors        | Simulation completes without uvm_fatal or equivalent failure. |
| No protocol timeouts   | AXI4-Lite and stream handshakes complete.                     |
| No unknown outputs     | No X/Z values appear after reset release.                     |
| Correct frame length   | Output pixel count matches expected frame size.               |
| Correct line length    | Each line contains expected number of pixels.                 |
| Correct pixel output   | Output matches reference model within tolerance.              |
| Correct register state | Readback matches expected configuration.                      |
| Correct status flags   | Error flags behave as expected.                               |
| Output image valid     | BMP or stream output can be decoded.                          |

A formal regression log should mark every test as **PASS**, **FAIL**, or **WAIVED WITH JUSTIFICATION**.

## 23.8 Software Reference Models

A software reference model provides expected output for comparison against RTL.

Reference models should be created for:

| **RTL Function**  | **Reference Model**                      |
|-------------------|------------------------------------------|
| RGB pass-through  | Direct input-to-output comparison        |
| Sharp/blur/emboss | 3×3 convolution model                    |
| Sobel             | Gradient and threshold model             |
| RGB to HSL        | Fixed-point compatible color conversion  |
| HSL to RGB        | Inverse conversion model                 |
| CCM               | Signed fixed-point 3×3 matrix model      |
| K-means           | Minimum-distance palette model           |
| Histogram         | Bin accumulation model                   |
| Local threshold   | Neighborhood threshold and average model |

A reference model must match the intended hardware precision. If RTL uses fixed-point rounding, saturation, or truncation, the model must apply the same policy.

## 23.9 Bit-Exact Versus Tolerance-Based Checking

Some modules should be checked bit-exactly. Others require tolerance because of division, rounding, or fixed-point approximation.

| **Module**            | **Recommended Checking**                |
|-----------------------|-----------------------------------------|
| Register readback     | Bit-exact                               |
| RGB pass-through      | Bit-exact                               |
| Palette lookup        | Bit-exact                               |
| K-means cluster index | Bit-exact                               |
| Histogram bin count   | Bit-exact                               |
| Convolution filters   | Bit-exact or ±1 LSB                     |
| RGB↔HSL conversion    | ±1 to ±2 LSB                            |
| CCM                   | ±1 LSB depending on coefficient scaling |
| Luminance conversion  | ±1 LSB                                  |
| UDP header fields     | Bit-exact                               |

Tolerance must be documented in the scoreboard and validation report.

## 23.10 Pipeline Latency Validation

Every processing block introduces latency. The expected output must be delayed to match the DUT output.

A latency validation method is:

1\. Drive a known marker pixel.

2\. Track the input cycle of the marker.

3\. Detect the output cycle of the corresponding result.

4\. Compute latency = output_cycle - input_cycle.

5\. Use this latency in the scoreboard alignment.

Recommended latency table:

| **Module**           | **Latency Item to Measure**        |
|----------------------|------------------------------------|
| RGB pass-through     | Baseline register delay            |
| HSL conversion       | Arithmetic pipeline delay          |
| CCM                  | Multiply-accumulate pipeline delay |
| Sobel                | Line-buffer plus arithmetic delay  |
| K-means              | Distance and comparator tree delay |
| Histogram            | Counter update latency             |
| Palette lookup       | Memory read latency                |
| UDP stream formatter | Header and packetization latency   |

Sideband signals such as valid, sof, eol, eof, tuser, and tlast must be delayed by the same effective latency as pixel data.

## 23.11 Frame and Line Validation

Video processing must preserve frame structure.

Validation checks:

pixels_per_line == expected_width

lines_per_frame == expected_height

total_pixels == expected_width × expected_height

SOF occurs at first pixel

EOL occurs at last pixel of each line

EOF occurs at last pixel of frame

A monitor should count:

- Pixels per line.

- Lines per frame.

- Frames processed.

- Unexpected gaps.

- Extra pixels.

- Missing pixels.

- Early eol.

- Missing sof.

Frame/line failures usually indicate timing, sideband alignment, or backpressure handling issues.

## 23.13 Debug Methodology

A disciplined debug process avoids random changes.

Recommended debug sequence:

1\. Reproduce the failure.

2\. Identify failing test and seed.

3\. Determine first mismatch time.

4\. Inspect input stimulus at mismatch.

5\. Inspect register configuration.

6\. Inspect internal pipeline stage.

7\. Inspect output alignment.

8\. Confirm reference model expectation.

9\. Apply minimal fix.

10\. Re-run failing test and regression subset.

The first mismatch is more useful than later mismatches because later errors may be secondary effects.

## 23.14 Debug Classification

Failures should be classified by category.

| **Category**      | **Examples**                                            |
|-------------------|---------------------------------------------------------|
| Stimulus error    | Bad input image, wrong sequence setup                   |
| Register error    | Wrong offset, missed write, bad reset value             |
| Protocol error    | AXI timeout, invalid response, stream handshake failure |
| Algorithm error   | Wrong equation, wrong coefficient order                 |
| Precision error   | Rounding, truncation, overflow                          |
| Alignment error   | Pipeline valid delay mismatch                           |
| Memory error      | FIFO, histogram, line-buffer, palette bank issue        |
| Integration error | Wrong mode connection or channel packing                |
| Tool/config error | Wrong simulation define, wrong image size macro         |

Classifying failures improves correction quality.

## 23.15 Common Simulation Failure Modes

| **Failure Mode**      | **Likely Cause**                                  | **Debug Action**                               |
|-----------------------|---------------------------------------------------|------------------------------------------------|
| Output image is black | VCP disabled, valid not asserted, wrong filter ID | Check control registers and valid path         |
| Output image shifted  | Pipeline latency mismatch                         | Compare SOF/EOL delay with RGB delay           |
| Red/blue swapped      | RGB/BGR packing mismatch                          | Inspect byte packing and channel order         |
| AXI write timeout     | Slave did not assert ready/response               | Check AXI4-Lite FSM                            |
| AXI read timeout      | Slave did not return RVALID                       | Check read address decode and response         |
| Wrong filter result   | Coefficient order mismatch                        | Verify k1–k9 mapping                           |
| HSL mismatch          | Fixed-point rounding difference                   | Compare intermediate hue/saturation/luminosity |
| K-means mismatch      | Distance/tie handling mismatch                    | Check palette and minimum-distance rule        |
| Histogram count low   | Read-modify-write hazard                          | Check consecutive same-bin handling            |
| X values in output    | Reset incomplete or uninitialized register        | Inspect reset sequence and default values      |

## 23.16 Hardware Validation Flow

After simulation passes, hardware validation confirms the implemented bitstream behaves correctly on the board.

Recommended hardware validation flow:

1\. Program FPGA bitstream.

2\. Confirm clocks and resets.

3\. Read VCP ID/status registers.

4\. Run RGB bypass mode.

5\. Enable test pattern mode.

6\. Enable simple filter mode.

7\. Enable camera input.

8\. Verify demosaic/RGB output.

9\. Enable VCP processing modes.

10\. Verify DisplayPort output.

11\. Verify Ethernet UDP output.

12\. Capture diagnostic counters.

Hardware validation must start simple. A live camera image should not be the first test. Begin with register readback and test patterns.

## 23.19 Output Image Validation

Recommended image validation methods:

| **Method**           | **Description**                                |
|----------------------|------------------------------------------------|
| Pixel-exact compare  | Every pixel must match exactly                 |
| Difference image     | Highlights mismatch locations                  |
| Histogram compare    | Compares distribution rather than exact pixels |
| Structural check     | Confirms frame size and channel order          |
| Visual inspection    | Final sanity check                             |

- Expected output image.

- Maximum error.

- Average error.

## 23.20 UDP and Host Validation

For Ethernet output, validate both packet structure and displayed image.

Checks:

| **Check**              | **Expected Result**                |
|------------------------|------------------------------------|
| Board IP reachable     | Host can communicate with board    |
| UDP packets received   | Receiver sees expected packet rate |
| Frame ID increments    | Frames are ordered                 |
| Packet ID increments   | Packet sequence is continuous      |
| Payload length correct | Receiver buffer does not overflow  |
| Header valid           | FFplay decodes stream              |

| Color order correct    | Test pattern colors match          |
| Frame rate stable      | No major drops under target mode   |

## 23.25 Common Hardware Validation Failures

| **Failure**                | **Likely Cause**                                  | **Correction**                                     |
|----------------------------|---------------------------------------------------|----------------------------------------------------|
| No image on display        | Clock/reset, video timing, or stream disabled     | Check clocks, status registers, and valid counters |
| Image appears but unstable | Timing or frame synchronization issue             | Check SOF/EOL/TLAST alignment                      |
| Wrong colors               | Bayer phase, RGB/BGR packing, or CCM coefficients | Use color-bar test                                 |
| UDP receives no data       | Network configuration or firewall                 | Verify IP, port, cable, and receiver               |
| Camera does not stream     | I2C configuration or MIPI mismatch                | Check sensor ID and receiver lock                  |
| VCP mode has no effect     | Register map or update request issue              | Read back control registers                        |
| Output freezes             | FIFO or DMA stall                                 | Check ready/valid and buffer status                |
| Random corruption          | CDC or timing issue                               | Review timing report and CDC paths                 |

## 23.26 Best Practices

1.  **Begin with the simplest mode.**  
    Verify reset, register readback, and RGB bypass before complex processing.

2.  **Use deterministic input images.**  
    Color bars, ramps, and checkerboards expose most channel and alignment errors.

3.  **Save expected, actual, and difference images.**  
    These artifacts make debug faster and document validation quality.

4.  **Use both automated and visual checking.**  
    Automated comparison catches exact mismatches; visual inspection catches perception-level issues.

5.  **Track pipeline latency explicitly.**  
    Incorrect latency alignment is one of the most common causes of false failures.

6.  **Use timeout detection on all bus transactions.**  
    A hung AXI transaction should fail clearly rather than stalling simulation indefinitely.

7.  **Validate each interface independently.**  
    Debug camera, VCP, register, display, and Ethernet paths one at a time.

8.  **Document every failure and fix.**  
    A repeatable debug log is part of a professional validation package.

## 23.27 Chapter Summary

This chapter described the simulation, validation, and debug methodology for the FPGA Video Color Processing System. The design uses image-based simulation, UVM transaction checking, AXI4-Lite timeout/error detection, waveform inspection, hardware debug counters, and board-level validation to confirm system correctness.

The source document shows that ModelSim simulation is used for module verification and that image-file testbenches can read stimulus images and generate output BMP files. It also shows that the AXI4-Lite driver includes explicit timeout and response-error checks, which are essential for robust debug.

A complete validation strategy must include block simulation, subsystem simulation, register testing, reference-model comparison, frame/line protocol checking, hardware bring-up, live sensor validation, UDP/display validation, and structured debug reporting. This creates a traceable path from RTL correctness to reliable real-time FPGA video operation.
