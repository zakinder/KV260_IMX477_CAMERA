# Chapter 12 — Color Correction Matrix

## 12.1 Overview

The **Color Correction Matrix (CCM)** is a pixel-transformation block used to adjust the red, green, and blue components of each input pixel. It applies a matrix multiplication to the RGB vector so that the output image can be corrected, enhanced, remapped, or transformed into a desired color response.

In the FPGA Video Color Processing System, the Color Correction Matrix is implemented as a selectable VCP function. The source design identifies the VCP module as supporting a Color Correction Matrix, K-means color clustering, test pattern generation, filters, and color-space conversions.

At a high level, the CCM block performs:

Input RGB Pixel

↓

Matrix Coefficient Selection

↓

3×3 Multiply-Accumulate

↓

Optional Bias / Offset Addition

↓

Clamp and Normalize

↓

Corrected RGB Output Pixel

The CCM is useful for camera color calibration, display matching, lighting compensation, artistic color manipulation, and programmable color transformation.

## 12.2 Purpose of the Color Correction Matrix

Camera sensors, lenses, lighting conditions, and displays do not always reproduce color identically. A red object under one light source may appear different under another light source. Similarly, a camera sensor may have different red, green, and blue sensitivity curves than a display panel.

The objective of the color adjustment matrix is to transform each pixel’s red, green, and blue channels to improve agreement between display output and light-source or sensor sensitivity. The source document states that the color adjust matrix transforms each pixel’s RGB channels to improve agreement with display and light-source sensitivity.

The CCM supports the following objectives:

| **Objective**         | **Description**                                                            |
|-----------------------|----------------------------------------------------------------------------|
| Sensor correction     | Compensates for camera sensor color-response differences.                  |
| Display matching      | Adjusts output so colors appear more consistent on the target display.     |
| Lighting compensation | Corrects color cast caused by warm, cool, or tinted lighting.              |
| Color manipulation    | Converts broad color ranges into altered or stylized colors.               |
| Calibration           | Applies measured correction coefficients from a color-calibration process. |
| Runtime tuning        | Allows software to select different coefficient sets for different scenes. |

## 12.3 Mathematical Model

The Color Correction Matrix treats each RGB pixel as a vector:

RGBin = \[Rin, Gin, Bin\]ᵀ

The corrected RGB output is generated by multiplying the input vector by a 3×3 coefficient matrix and optionally adding an offset vector:

\[Rout\] \[C00 C01 C02\] \[Rin\] \[O0\]

\[Gout\] = \[C10 C11 C12\] \[Gin\] + \[O1\]

\[Bout\] \[C20 C21 C22\] \[Bin\] \[O2\]

Expanded form:

Rout = C00×Rin + C01×Gin + C02×Bin + O0

Gout = C10×Rin + C11×Gin + C12×Bin + O1

Bout = C20×Rin + C21×Gin + C22×Bin + O2

Where:

| **Term**         | **Description**                        |
|------------------|----------------------------------------|
| C00–C22          | Color correction coefficients          |
| O0, O1, O2       | Optional output offsets or bias values |
| Rin, Gin, Bin    | Input RGB channel values               |
| Rout, Gout, Bout | Corrected RGB output channel values    |

The source document describes the color adjust matrix as being expressible as a 3×3 matrix and uses “CAM” to denote color-adjust matrix RGB values.

## 12.5 Input and Output Pixel Format

The CCM block operates on RGB pixel data after demosaic conversion.

A typical 8-bit RGB input is:

Rin, Gin, Bin ∈ \[0, 255\]

A typical 10-bit RGB input is:

Rin, Gin, Bin ∈ \[0, 1023\]

The output should preserve the selected channel width:

Rout, Gout, Bout ∈ valid channel range

For AXI4-Stream RGB888, packing may be:

TDATA\[23:16\] = R

TDATA\[15:8\] = G

TDATA\[7:0\] = B

For RGB 10-bit-per-channel, packing may be:

TDATA\[29:20\] = R

TDATA\[19:10\] = G

TDATA\[9:0\] = B

The input and output packing must be consistent with the VCP datapath definition.

## 12.6 Identity Matrix Mode

The identity matrix leaves the input RGB value unchanged:

\[1 0 0\]

\[0 1 0\]

\[0 0 1\]

The corresponding equations are:

Rout = Rin

Gout = Gin

Bout = Bin

Identity mode is useful for:

- Baseline testing.

- Bypass comparison.

- Debugging coefficient loading.

- Verifying output clamping.

- Measuring CCM latency without image modification.

The CCM register map should include an identity matrix as the default safe configuration.

## 12.7 Coefficient Matrix Configuration

The design document includes multiple **Color Adjust Matrix (CAM)** coefficient sets organized by color-manipulation index. For example, Color Manipulation Index \#01 includes CAM-1, CAM-2, and CAM-3 matrices.

A practical CCM design may support several coefficient banks:

CAM-0 = Identity / bypass

CAM-1 = Strong color manipulation

CAM-2 = Moderate color adjustment

CAM-3 = Light color adjustment

CAM-N = User-programmable matrix

The active matrix is selected by i_k_config_number or by an AXI4-Lite register.

## 12.9 Coefficient Interpretation

Each output channel is a weighted mixture of all three input channels.

### 12.9.1 Red Output Row

Rout = C00×Rin + C01×Gin + C02×Bin + O0

- C00 controls how much input red contributes to output red.

- C01 controls how much input green contributes to output red.

- C02 controls how much input blue contributes to output red.

### 12.9.2 Green Output Row

Gout = C10×Rin + C11×Gin + C12×Bin + O1

- C10 controls red contribution to output green.

- C11 controls green contribution to output green.

- C12 controls blue contribution to output green.

### 12.9.3 Blue Output Row

Bout = C20×Rin + C21×Gin + C22×Bin + O2

- C20 controls red contribution to output blue.

- C21 controls green contribution to output blue.

- C22 controls blue contribution to output blue.

A positive coefficient increases contribution. A negative coefficient subtracts contribution. Coefficients above 1.0 amplify the corresponding channel contribution.

## 12.10 Fixed-Point Coefficient Representation

The CCM should use fixed-point coefficients for FPGA implementation. Floating-point arithmetic is usually unnecessary and expensive in real-time video pipelines.

A practical fixed-point format is:

Coefficient format: signed Q4.12

Scale factor: 2^12 = 4096

Example coefficient conversion:

1.500 → round(1.500 × 4096) = 6144

-0.250 → round(-0.250 × 4096) = -1024

The multiplication is performed as integer arithmetic:

product = input_channel × coefficient_fixed

After accumulation, the result is shifted back:

output_unclamped = accumulated_value \>\> 12

### 12.10.1 Recommended Bit Widths

For 8-bit input and Q4.12 coefficients:

| **Signal**          | **Recommended Width** |
|---------------------|-----------------------|
| Input channel       | 8 bits unsigned       |
| Coefficient         | 16 bits signed        |
| Product             | 24 bits signed        |
| Three-product sum   | 26 bits signed        |
| Offset              | 16–26 bits signed     |
| Output before clamp | 16–26 bits signed     |
| Final channel       | 8 bits unsigned       |

For 10-bit input, product and accumulator widths should be increased accordingly.

## 12.11 Hardware Multiply-Accumulate Architecture

The CCM datapath is a three-row multiply-accumulate structure.

┌── C00 × R ──┐

Rout row: ├── C01 × G ──┼── Sum ── Offset ── Clamp ── Rout

└── C02 × B ──┘

┌── C10 × R ──┐

Gout row: ├── C11 × G ──┼── Sum ── Offset ── Clamp ── Gout

└── C12 × B ──┘

┌── C20 × R ──┐

Bout row: ├── C21 × G ──┼── Sum ── Offset ── Clamp ── Bout

└── C22 × B ──┘

A fully parallel implementation uses nine multipliers:

| **Output Channel** | **Multipliers** |
|--------------------|-----------------|
| Red row            | 3               |
| Green row          | 3               |
| Blue row           | 3               |
| Total              | 9               |

This allows one pixel per clock after pipeline fill.

## 12.12 Resource-Optimized Architecture

If FPGA resources are limited, the CCM can share multipliers over multiple cycles. However, this may reduce throughput.

**Fully Parallel CCM**

| **Feature**    | **Description**                 |
|----------------|---------------------------------|
| Multipliers    | 9                               |
| Throughput     | 1 pixel per clock               |
| Latency        | Low to medium                   |
| Resource usage | Higher                          |
| Use case       | High-resolution real-time video |

**Shared-Multiplier CCM**

| **Feature**    | **Description**                                  |
|----------------|--------------------------------------------------|
| Multipliers    | 1 to 3                                           |
| Throughput     | Lower unless clock is much faster                |
| Latency        | Higher                                           |
| Resource usage | Lower                                            |
| Use case       | Low-resolution video or non-real-time processing |

For real-time high-resolution video, the fully parallel or deeply pipelined architecture is preferred.

## 12.13 Pipeline Stages

A practical CCM pipeline can be divided into deterministic stages:

| **Stage** | **Function**                                 |
|-----------|----------------------------------------------|
| Stage 0   | Register input RGB and valid signal          |
| Stage 1   | Read or select active coefficient matrix     |
| Stage 2   | Multiply RGB channels by matrix coefficients |
| Stage 3   | Sum products for each output row             |
| Stage 4   | Add output offsets                           |
| Stage 5   | Round and scale fixed-point results          |
| Stage 6   | Clamp to valid RGB range                     |
| Stage 7   | Register output RGB                          |

Pipeline flow:

RGB In

→ Coefficient Select

→ 9 Parallel Multipliers

→ 3 Row Accumulators

→ Offset Add

→ Scale / Round

→ Clamp

→ RGB Out

The valid and sideband signals must be delayed by the same number of pipeline stages.

## 12.14 Offset and Bias Handling

Some matrix sets include a fourth value per row or an output offset. In the source CAM examples, values appear after the three matrix coefficients, indicating a per-row bias or output adjustment term.

The matrix can therefore be treated as a 3×4 transform:

\[Rout\] \[C00 C01 C02 O0\] \[Rin\]

\[Gout\] = \[C10 C11 C12 O1\] \[Gin\]

\[Bout\] \[C20 C21 C22 O2\] \[Bin\]

\[1\]

Expanded:

Rout = C00×Rin + C01×Gin + C02×Bin + O0

Gout = C10×Rin + C11×Gin + C12×Bin + O1

Bout = C20×Rin + C21×Gin + C22×Bin + O2

Bias values should use the same fixed-point scale as the accumulated result, or they should be converted before addition.

## 12.15 Output Clamping

Matrix multiplication can produce negative values or values above the maximum channel range. Therefore, the CCM output must be clamped.

For 8-bit output:

if value \< 0:

output = 0

else if value \> 255:

output = 255

else:

output = value

For 10-bit output:

if value \< 0:

output = 0

else if value \> 1023:

output = 1023

else:

output = value

Clamping prevents wraparound artifacts such as negative values appearing as bright pixels due to unsigned conversion.

## 12.16 Rounding and Scaling

Fixed-point matrix results should be rounded before shifting to the final output width.

If the coefficient format has F fractional bits:

rounded = accumulated + 2^(F-1)

scaled = rounded \>\> F

For Q4.12 coefficients:

rounded = accumulated + 2048

scaled = rounded \>\> 12

Rounding improves numerical accuracy compared with truncation.

## 12.17 Matrix Bank Selection

The input i_k_config_number can be used to select between predefined matrix banks.

A representative bank table is:

| **Config Number** | **Matrix Function**         |
|-------------------|-----------------------------|
| 0                 | Identity / bypass           |
| 1                 | CAM-1 color manipulation    |
| 2                 | CAM-2 color manipulation    |
| 3                 | CAM-3 color manipulation    |
| 4                 | Warm-light correction       |
| 5                 | Cool-light correction       |
| 6                 | High-saturation enhancement |
| 7                 | User-programmable matrix    |

The selected matrix should be latched at a frame boundary:

Software writes pending matrix index

↓

Start-of-frame detected

↓

Pending index becomes active

↓

Entire frame uses one matrix configuration

This avoids partial-frame color changes.

## 12.19 Runtime Coefficient Update Strategy

Runtime coefficient updates must be handled carefully. If software writes matrix coefficients while a frame is being processed, the frame may show partial color shifts.

A safe update method is:

Software writes new coefficients to shadow registers

↓

Software sets update request

↓

CCM waits for start-of-frame

↓

Shadow coefficients copy to active coefficients

↓

Update done flag is set

This strategy guarantees that one complete frame uses one consistent coefficient set.

### 12.19.1 Active and Shadow Registers

| **Register Type**   | **Purpose**                                  |
|---------------------|----------------------------------------------|
| Active coefficients | Used by the real-time pixel datapath.        |
| Shadow coefficients | Written by software while video is running.  |
| Pending update flag | Indicates software has requested activation. |
| Update done flag    | Indicates new matrix has become active.      |

This active/shadow method is recommended for stable live-video operation.

## 12.20 Sideband Signal Alignment

The CCM introduces pipeline latency. AXI4-Stream sideband signals must be delayed to match the corrected RGB data.

Signals requiring alignment include:

- TVALID

- TUSER

- TLAST

- Pixel coordinates

- Frame counters

- Line counters

Example delay pipeline:

RGB data pipeline: P0 → P1 → P2 → P3 → P4 → P5

TUSER pipeline: U0 → U1 → U2 → U3 → U4 → U5

TLAST pipeline: L0 → L1 → L2 → L3 → L4 → L5

TVALID pipeline: V0 → V1 → V2 → V3 → V4 → V5

The output sideband signals should be taken from the final delay stage.

## 12.21 Throughput Requirement

The preferred CCM throughput is:

1 pixel per clock

To sustain this throughput:

- Coefficients must be available every cycle.

- Multipliers must be pipelined.

- Accumulators must accept new values every cycle.

- Clamp logic must be registered.

- AXI4-Stream backpressure must be handled correctly.

For high-resolution video, a fully pipelined nine-multiplier architecture is the most direct implementation.

## 12.22 Latency Model

A representative CCM latency model is:

| **Block**          | **Example Latency** |
|--------------------|---------------------|
| Input register     | 1 cycle             |
| Coefficient select | 1 cycle             |
| Multiply stage     | 1–3 cycles          |
| Accumulation stage | 1–2 cycles          |
| Offset addition    | 1 cycle             |
| Round and scale    | 1 cycle             |
| Clamp stage        | 1 cycle             |
| Output register    | 1 cycle             |

The exact latency depends on DSP configuration and pipeline depth. The valid and sideband delay chains must use the same latency value.

## 12.23 Resource Considerations

The CCM mainly consumes DSP blocks, LUTs, flip-flops, and registers.

| **Resource**     | **Usage**                                         |
|------------------|---------------------------------------------------|
| DSP blocks       | Matrix coefficient multiplications                |
| LUTs             | Coefficient selection, clamp logic, control logic |
| Flip-flops       | Pipeline registers and sideband delay             |
| BRAM / LUTRAM    | Optional coefficient-bank storage                 |
| AXI interconnect | Register programming through AXI4-Lite            |

Resource optimization options include:

- Use fewer coefficient banks.

- Store coefficients in distributed ROM.

- Share multipliers at lower throughput.

- Use shift-add approximations for simple coefficients.

- Use DSP cascade paths for accumulation.

- Limit coefficient precision where acceptable.

## 12.26 Common Failure Modes

| **Failure Mode**              | **Likely Cause**                                 | **Correction**                           |
|-------------------------------|--------------------------------------------------|------------------------------------------|
| Colors appear swapped         | Incorrect RGB packing or matrix row mapping      | Verify channel order                     |
| Output too bright             | Missing scale shift or excessive coefficient sum | Apply fixed-point scaling and clamp      |
| Output too dark               | Incorrect coefficient scaling                    | Verify Q-format conversion               |
| Negative values appear bright | Signed value cast to unsigned                    | Clamp negative values before packing     |
| Frame has two color styles    | Matrix updated mid-frame                         | Use shadow-to-active frame update        |
| Output delayed incorrectly    | Sideband latency mismatch                        | Delay TUSER, TLAST, and TVALID           |
| Severe saturation             | Coefficients too large                           | Reduce matrix gain or add normalization  |
| No color change               | Matrix not loaded or bypass active               | Verify register control and active index |

## 12.27 Hardware Design Recommendations

1.  **Use signed fixed-point coefficients.**  
    Color correction often requires negative off-diagonal terms.

2.  **Use a fully pipelined multiply-accumulate structure for real-time video.**  
    This supports one-pixel-per-clock throughput.

3.  **Include identity bypass mode.**  
    Identity mode provides a safe fallback and validation baseline.

4.  **Use active/shadow coefficient registers.**  
    This prevents partial-frame color artifacts.

5.  **Clamp final outputs.**  
    Never allow signed or overflowed results to wrap into packed RGB output.

6.  **Document coefficient Q-format.**  
    Software and hardware must use the same scaling convention.

7.  **Delay sideband signals to match CCM latency.**  
    Frame and line markers must remain aligned with corrected pixels.

8.  **Validate against a software model.**  
    Pixel-level reference comparison is essential for signed matrix arithmetic.

## 12.28 Chapter Summary

This chapter described the Color Correction Matrix architecture used in the FPGA Video Color Processing System. The CCM transforms each RGB pixel using a 3×3 matrix and optional bias terms. It can be used for sensor correction, display matching, lighting compensation, color enhancement, and programmable color manipulation.

The source design defines the Color Correction Matrix block with configuration-number input, clock, reset, input RGB channel, coefficient input, and output RGB channel. It describes the color adjust matrix as a 3×3 matrix used to transform RGB pixel channels and identifies CAM values as the color-adjust matrix coefficients.

A reliable FPGA CCM implementation requires signed fixed-point coefficients, pipelined multiply-accumulate logic, output clamping, frame-safe coefficient updates, and sideband alignment. When properly implemented, the CCM provides a flexible and efficient hardware block for real-time color calibration and color manipulation.
